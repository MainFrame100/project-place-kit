# github — сначала проверка, потом публикация

Команда одна, порядок всегда такой. Ни один шаг не пропускается, `--no-verify` не используется.

## 1. Свежая версия

`git pull --ff-only` (если репозиторий уже на GitHub). Не прошёл — сказать человеку и не продолжать: расхождение разбирается, не затирается.

## 2. Проверка

`python automation/publish_check.py`. Он смотрит: секреты в текстах (по-русски и по-английски, `automation/redact.py`), секретные файлы в git, `.gitignore`, README в каждой папке проекта, новые файлы в корне, скрипты вне `automation/`, правки сырья, удаления в журнале, дату «Обновлено» в статусе, README папок при добавлении и удалении файлов, закрыт ли репозиторий на GitHub, если он уже привязан.

## 3. Исправление

Каждое `✗` исправить и запустить проверку снова — до «Проверка пройдена». Что делать:

| Ошибка | Действие |
|---|---|
| секреты в тексте | `python automation/redact.py <путь>` — значение станет `[скрыто: пароль]`, ссылка на сообщение останется |
| секретный файл в git | `git rm --cached <файл>`, строка в `.gitignore` |
| нет README в папке | написать: что в папке, где что лежит; README родителя — дополнить строкой |
| новый файл в корне | перенести в свою папку: скрипты → `automation/`, проектное → `projects/<имя>/` |
| правка сырья | вернуть файл (`git checkout -- <файл>`), новое положить новым файлом. Разрешено без ошибки: дописать выгрузкой `tg_export.py`, скрыть секрет `redact.py` |
| репозиторий открытый | `gh repo edit --visibility private --accept-visibility-change-consequences`, затем проверка снова |
| удалены строки в журнале | вернуть, уточнение записать новой записью «со слов …, дата». Сегодняшнюю запись править можно — она черновик |

`!` — предупреждения: прочитать, поправить, если по делу (обновить дату «Обновлено», дописать README).

## 4. Коммит

Один смысловой блок — один коммит. Сообщение по-русски, повелительное наклонение, до 72 символов, без точки, без упоминания ИИ:

```
<тип>(<область>): <что сделать>
```

Типы: `feat` новое · `fix` исправление · `docs` документы и README · `chore` настройки, зависимости · `sync` обновление статусов и журналов из источников.
Области: `<имя проекта>`, `automation`, `skills`, `rules`.

Примеры: `sync(o3): статус и журнал за 2026-09-01…09-08` · `feat(automation): tg_export — выгрузка тем форума` · `docs(o3): README проекта — карта материалов`.

Перед коммитом — `git diff --cached --stat`: если в нём два разных дела (статус клиента и правка скрипта) — два коммита.

## 5. Публикация

- Репозиторий уже на GitHub: `git push`.
- Первая публикация, по порядку:
  1. `git remote -v`. `origin` смотрит на чужой набор (`project-place-kit`) — `git remote remove origin`. Туда пушить нельзя.
  2. `git config user.name` и `user.email` пустые — спросить человека, выставить.
  3. `gh auth status`; не вошёл — **человек** входит через `gh auth login --web`.
  4. `gh repo create <имя> --private --source=. --push`.
  5. Ревизия закрытости: `gh repo view --json isPrivate` → `true`. Человек сам открывает страницу репозитория и видит метку Private — сказать ему это сделать. Не `true` — `gh repo edit --visibility private --accept-visibility-change-consequences`, и снова `gh repo view`. Данные проектов — только закрытый репозиторий, всегда.
- Сказать человеку: адрес, что вошло (сколько файлов, какие коммиты), какие предупреждения остались. Доступ коллеге: Settings → Collaborators.

## Когда публиковать

Сразу после того, как обновлён статус или журнал проекта, добавлен скрипт или правило. Не копить: у команды должна быть свежая версия, а у нейронки каждого — одна и та же папка.

## Чего не делать

- Не коммитить при `✗` — ни «пока так», ни «потом почищу».
- Опубликованную ветку, которую тянет кто-то ещё, не переписывать: `push --force`, `rebase` — нет. Коллега потеряет свои правки, а журнал — смысл «видно, что было».
- Единственное исключение — в историю попал пароль или ключ. Порядок: сначала сменить сам секрет (он уже утёк — GitHub кэширует, коллеги стянули), потом вычистить историю (`git filter-repo`), потом `push --force` и сказать всем сделать свежий клон. Чистка без смены секрета бесполезна.
- Не публиковать данные проектов в открытый репозиторий.
