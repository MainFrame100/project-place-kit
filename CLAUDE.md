# Правила репозитория

Здесь живут проекты: по каждому — папка в `projects/` с сырьём, журналом и тремя документами. Нейронка собирает, человек проверяет. Для команды это источник правды: если здесь и где-то ещё написано по-разному, верно то, что здесь.

## Структура

- `projects/<проект>/` — один проект = одна папка: `README.md`, `sources/`, `journal/`, `passport.md`, `status.md`, `materials.md`. Как завести — `projects/README.md`.
- `automation/` — все скрипты. Скрипт не живёт в папке проекта.
- `.claude/skills/` — как делать типовую работу: `project-status` (сырьё → журнал → документы → проверка), `github` (проверка → исправление → публикация), `quality-check` (проверка длинного артефакта перед сдачей; подтягивается при установке).
- `SETUP.md` — установка и подключения. Читать, когда человек просит «настрой».
- README.md есть в каждой папке — читать до работы в ней. Изменил структуру — обнови README.

## Факты

- Каждый факт — со ссылкой: `источник | дата | автор → кому | «цитата» | #сообщение или файл`. Нет ссылки — `[GAP]`, не факт. Как оформлять ссылку — раздел «Документы».
- Отсутствие упоминания ≠ доказательство. Вывод не шире цитаты. «Отчитался» ≠ «проверили» ≠ «клиент принял». «Решили» ≠ «обсудили» ≠ «предложили».
- Один случай — не система: «всегда», «системно» — только от трёх независимых случаев.
- Источники противоречат — показать оба, не усреднять. Автор мысли — кто сказал первым. Даты только абсолютные.
- Метки: `[CONFIRMED: источник]` / `[GAP]` / `[ADDED]`.
- Правка человека — новый факт со своим источником в журнал. Старое не затирается. `sources/` не правится.
- Нет в материалах — так и сказать. Не заполнять «для полноты».

## Документы

- Одна мысль — одна строка. Списки, не абзацы. Абзац длиннее двух строк — разбить.
- Сначала суть, потом детали. Термины без пояснения не использовать.
- Якорь — кликабельная ссылка на файл источника с номером сообщения: `[чат #102](sources/telegram-vektor-proekt.md)`. Голый `#102` без ссылки — не якорь.
- «Ситуация на сегодня» в статусе — 5–8 строк списком, каждая с датой и якорем.
- Карта материалов — только ключевое: сайт, CRM, описание продукта и аудитории, где лежат отчёты, договор, где хранятся доступы (сами доступы — нет). Ссылки кликабельные. Итоги созвонов, переписка и разовые файлы в карту не идут — они в журнале.
- Таблица — до пяти колонок. Длинное — в журнал, не в документ.

## Безопасность

- Ключи, пароли, токены, доступы — только в `.env`. Ни в один другой файл: ни в журнал, ни в статус, ни в README. Пароль в источнике — в файлы не переносить: `[скрыто: пароль]` и ссылка на сообщение.
- Выгрузка чатов проходит через `automation/redact.py` сама: русские и английские слова с опечатками («пароль», «пасс», «лог/пас», «токен», password, api key, credentials) и форматы ключей.
- Публикация — только по скиллу `github`: `python automation/publish_check.py` → исправить всё `✗` → коммит → push. С ошибками проверки не публиковать. После первой публикации — убедиться, что репозиторий закрыт (Private), и показать это человеку.
- `.env`, `*.session`, `.venv/` — в `.gitignore`, не трогать.
- Данные проектов — только закрытый репозиторий.

## Агенты и модели

- Поиск, разбор длинных файлов, проверка — субагентами. В основной контекст попадает результат, не сырьё. Одна задача = один агент. Сырьё до ~300 сообщений — читать самому, без субагента: он дороже по времени, чем чтение.
- Модель — по задаче, не одна на всё. Названия меняются, уровень остаётся: старшая модель линейки (на 09.2026 — Claude Opus, старшая GPT sol medium) — выводы, синтез, спорные места, проверка; средняя (Claude Sonnet, GPT Terra medium) — сбор, извлечение фактов по правилам, разбор сырья, черновики. Самую младшую не использовать: она пропускает факты.
- Проверяет не тот агент, который писал. Проверяльщик и скептик — старшей моделью. Нет субагентов (например, Codex) — проверка отдельным запросом с чистого листа после сбора, не в том же ответе.

## Разработка

- Повторяемое — скриптом в `automation/`, с описанием в `automation/README.md`. Не решать каждый раз заново.
- Перед запуском Python — активировать `.venv`.
- Автоматику проверять на 1–2 элементах до полного прогона.
- Файлы в корне не создавать без просьбы.
- «Готово» = показан фактический результат. Массовая операция — сколько обработано, сколько пропущено, почему.
